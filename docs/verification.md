## Task A — виправлення за скілом Vercel

Щонайменше 2 виправлення (досить двох); для **одного** (на ваш вибір) — числа до/після, для решти
досить id правила й пояснення.

**Як міряли (для виправлення з числами):** продакшн-збірка (`npm run build && npm start`), порт
3000. Команди — саме ті, що в `docs/walkthrough.md` крок 4: 1 прогрів + 3 прогони `curl -s -o
/dev/null -b "$C" -w "TTFB %{time_starttransfer}s, total %{time_total}s\n" "$U"` на
`http://localhost:3000/dashboard` з cookie `leaddesk_session=demo-u_olena`. «Було» — вимірювалось з
чистого коду `main` (обидва виправлення тимчасово відкладені через `git stash`), «стало» — лише з
одним застосованим виправленням `async-parallel` (друге виправлення на той момент теж було
відкладене, щоб не змішувати ефекти двох фіксів в одному вимірі).

| Правило (id) | Коміт | Файли | Що змінилось | Було (`main`) | Стало | Як міряли |
|---|---|---|---|---|---|---|
| `async-parallel` | `0fd3b5b` | `app/dashboard/page.tsx` | `getLeads`/`getLeadStats`/`getSourceBreakdown` (незалежні одне від одного) — з трьох послідовних `await` на один `Promise.all` | TTFB ≈ 2.24s (2.242 / 2.249 / 2.238) | TTFB ≈ 1.43s (1.429 / 1.431 / 1.428) | `curl` TTFB, 3 прогони, продакшн-збірка (команди вище) |
| `server-cache-react` | `6b5d944` | `lib/data.ts` | `getCurrentUser` обгорнуто в `React.cache()` (як уже було зроблено для `getWorkspace`) | (без заміру часу — див. пояснення нижче) | (без заміру часу) | — |

- Чому обрали для заміру саме `async-parallel`: це саме та причина, яку описує робоча ситуація
  завдання («дашборд відкривається понад 2 секунди») — `getLeadStats` (1200 мс) блокував і `getLeads`
  (400 мс), і `getSourceBreakdown` (400 мс), хоча жоден з трьох не залежить від результату іншого.
  Ефект найпростіше й найчесніше видно саме в TTFB продакшн-збірки.
- Друге виправлення (`server-cache-react`) — що і чому змінили, як переконались, що не зламали:
  `getCurrentUser()` викликається незалежно в `app/dashboard/layout.tsx`, `components/dashboard-header.tsx`
  і `app/dashboard/page.tsx` — тобто тричі за один рендер `/dashboard` (саме цей сценарій міряли нижче).
  Є ще четверте місце виклику — `app/dashboard/leads/[id]/page.tsx` — але воно не бере участі в цьому
  вимірі, бо це інший маршрут, який рендериться окремим запитом. Жоден з викликів не був
  мемоізований (на відміну від `getWorkspace`, який уже обгорнуто в `cache()`). Замість числа TTFB
  виміряли те, що напряму показує ефект дедуплікації — лічильник `db:getUserBySession` у
  server-логах за один запит `/dashboard`: **3 виклики до фіксу → 1 виклик після** (перевірено тим
  самим прийомом: тимчасово відкладали фікс через `git stash`, білдили, робили один `curl` на
  `/dashboard`, дивились лічильник у логах `npm start`). Переконались, що нічого не зламали:
  `npm run lint` і `npm run build` пройшли чисто після кожного з двох комітів, а дашборд і сторінка
  ліда відкриваються й показують ті самі дані (перевірено в браузері після фінальної збірки).
- Порада скіла, яку звірили з документацією Next.js 16 і **не** застосували або змінили — і чому:
  жодну з двох застосованих порад не довелось відхиляти чи змінювати — обидві підтверджені
  `node_modules/next/dist/docs/` без розбіжностей (деталі — `docs/skill-review.md`, розділ 5). Інші
  правила скіла (наприклад `bundle-dynamic-imports` для важкого імпорту `exceljs` у
  `components/leads-toolbar.tsx`, або `server-serialization` для того, що `LeadsTable` отримує повний
  об'єкт `Lead` з `rawPayload`/`internalNotes`/IP разом із полями, які реально рендеряться) теж
  застосовні, але не входять до цих двох комітів — двох виправлень (як дозволяє рубрика) вистачило.
- Якщо виміряне виправлення не змінило чисел — чому: змінило — TTFB впав з ~2.24s до ~1.43s (≈36%).
  Проста арифметика (100+100+max(400,1200,400)=1400 мс проти 100+100+400+1200+400=2200 мс
  послідовно) наближено збігається зі спостереженими числами, але це спрощена модель — вона не
  враховує, що `layout.tsx` і `page.tsx` Next.js рендерить як окремі, паралельні сегменти, тому три
  виклики `getCurrentUser()` (з попереднього пункту, 100 мс кожен) не обов'язково лежать на
  критичному шляху так само лінійно, як показує ця формула. Самі виміряні числа (2.24s / 1.43s) —
  реальні curl-заміри, а не розрахунок; формула вище — лише орієнтовне пояснення «чому», а не строге
  виведення.
- `npm run lint`, `npm run build` після виправлень: обидва пройшли чисто після кожного з двох
  комітів (`0fd3b5b`, `6b5d944`) і після фінальної збірки з обома фіксами разом.
